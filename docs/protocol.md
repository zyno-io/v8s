# Agent ↔ UI protocol (v1)

The source of truth is [`agent/pkg/protocol/protocol.go`](../agent/pkg/protocol/protocol.go); TypeScript types are generated from it (`yarn protocol:gen` → `packages/client/src/protocol.gen.ts`). This page explains the behaviour the types cannot. Background: [performance.md §9](performance.md#9-wire-protocol-and-sync).

## Connection

- One **data socket** per browser tab: `GET /ws`, WebSocket, binary frames only.
- **Desktop / `v8s serve`**: the client offers `Sec-WebSocket-Protocol: v8s.v1, token.<hex>`. The agent rejects a missing or wrong token, and an `Origin` that is not the agent's own origin (or the Electron app origin), with 403 before upgrading. It echoes `v8s.v1`.
- **Fake mode** (`v8s agent --fake …`, used by tests and UI development) still requires the token, but it is printed to stdout like in desktop mode.
- On upgrade the agent sends `Hello`. The client checks `version == 1` and closes on mismatch.

## Frames

`[u8 kind][u32 channel BE][u32 seq BE][msgpack payload]`. `seq` increments by one for every frame the agent sends. The client sends `seq = 0` except on acks.

| Kind | Direction | channel | Payload |
| --- | --- | --- | --- |
| 1 Hello | agent → client | 0 | `Hello` |
| 2 Request | client → agent | request id | `Request` |
| 3 Response | agent → client | request id | `Response` |
| 4 Patch | agent → client | qid | `ViewPatch` |
| 5 Ack | client → agent | 0 | none (`seq` = acked patch frame) |
| 6 Dict | agent → client | 0 | `DictAdd` |
| 7 ClusterState | agent → client | 0 | `ClusterStates` |
| 8 Object | agent → client | oid | `ObjectFrame` (not acknowledged) |
| 9 Job | agent → client | 0 | `JobFrame`: the whole current state of one job (not acknowledged) |

msgpack: maps with the field names in the Go tags; `ids` is a msgpack `bin`. Go uses `github.com/vmihailenco/msgpack/v5`, the client `msgpackr` (with `useRecords: false`, `mapsAsObjects: true`).

## Views

1. `view.subscribe {qid, gen, query, window}` → `{columns}`. The agent then sends a full first patch (with `ids`) as soon as rows exist, and later patches as things change.
2. **Coalescing**: the first change after a quiet period flushes within 16 ms; after that at most one patch per subscription per tick. The tick is 100 ms for loopback clients and 250 ms otherwise (P0 only implements loopback). A paused subscription (P1: hidden tab) gets no ticks.
3. **Backpressure**: at most 3 unacknowledged patch frames or 512 KiB in flight per socket; beyond that the subscription stays dirty and the next tick sends the newest state. Never a backlog.
4. **Generations**: `view.update` with a new `query` must bump `gen`; the agent ignores an update whose `gen` is lower than the subscription's current one. Updates of one subscription apply in request order: while one is resolving a first-time generic kind (up to 20 s) later ones queue behind it, and a later one that changes the query supersedes it (the superseded request answers `conflict`). Patches carry the `gen` they were computed for; the client drops patches older than its current `gen`.
5. **Windows**: the client asks for `limit` rows from `offset`. With `anchorId` set (the first visible row), `offset` is relative to the anchor's current index, so inserts above the viewport never move what the user is reading. The agent clamps the window to the view. If the anchor row is gone, or it changed and re-sorted outside the window the client holds, the window keeps its previous position instead of chasing it.
6. **Ids**: per subscription, monotonic, never reused. A row's id stays stable while the object exists in the view (including across re-sorts and query changes on the same subscription).
7. **Rows**: `[id, version, …cells]` in `columns` order; `version` increases when any cell changes. The client keeps rows by id and re-renders a row only when its version changes.

### Events of one object

`view.subscribe` with `gvr: "v1/events"` and `query.involved: ObjectRef` (`{cluster, gvr, namespace, name}`) is the view of **every** event, Normal and Warning, of that one object, listed on demand while the view is open (the global `v1/events` view is Warning-only). The agent resolves the object's Kind and scope itself and starts a namespaced, reference-counted LIST + WATCH of its events (`involvedObject.kind`, `.name`, `.namespace`; no uid: the kubelet records Node events with the node name as uid). The query is then rewritten into a plain filtered view (`clusters = [involved.cluster]`, the events namespace, and an `object eq Kind/name` filter) over one shared per-cluster events store, so patches, windows, backpressure and the columns (the `v1/events` columns, including `source`) work as in any other view. `text`, `filters` and `sort` still apply; `clusters` and `namespaces` are ignored.

- The events namespace is the object's own, or `default` for a cluster-scoped object (Node, PersistentVolume, Namespace, cluster-scoped custom resources). The kind and its scope come from the agent's registry or discovery, never from the client.
- The agent keeps the newest `MaxObjectEvents` (200) events per object by `lastSeen`.
- `view.subscribe` answers only after the first list, an error, or 15 s, so the client has a real loading state and a real error. An error response means no subscription exists. `bad_request`: `gvr` other than `v1/events`, a missing name or namespace, a kind that has no events (`helm.sh/v1/releases`, `v8s/v1/problems`), or a direct query of the internal `v8s/v1/objectevents` kind. `not_found`: the cluster is not selected, or the kind is unknown. `forbidden`: no permission to list events in that namespace. `unavailable`: the 15 s timeout or the watch budget is exhausted.
- `view.update` that changes the `involved` object (cluster, gvr, namespace or name) re-resolves like a changed kind; one that keeps it only changes sort, filters or the window.
- Unsubscribing releases the watch, which lingers 30 s (it counts against the per-cluster watch budget and is evicted first). These rows live in their own store: they never reach the Warning-only tier-0 events or the problems engine.

## Requests

Every request is a `Request{method, params}` on a fresh channel id answered by one `Response{result | error}`. Errors are `{code, message, hint?, live?, applied?}`; codes: `bad_request`, `not_found`, `forbidden`, `unavailable`, `internal`, `invalid` (the API server rejected the object), `conflict`, `write_unavailable`, `write_confirm`, `link_mismatch`, `gitops_managed`. Slow requests (object operations, a generic kind's first view) are answered asynchronously, so responses may arrive out of order with patches; match them by channel id.

A hit is `{cluster, gvr, namespace?, name, field, label, value, match, detail?}`; `match` is `exact`, `contains` (the object's CIDR or range holds the address), `within`, `overlap` or `prefix`. Groups are ordered by best match, then kind. Each object yields one hit. The name search still runs, so a wrong detection (`v1.2`) only adds an empty IP section. `pending` lists sources still loading (`{cluster, kind?}`, no `kind` = discovery not loaded yet): ask again shortly (the UI retries at most 5 times, 600 ms apart). `skipped` lists sources that could not be read (`reason`: `forbidden`, `not found`, `budget` when the cluster is at its watch limit, or `error` when the watch could not start for another reason). A weak query (a prefix with fewer than two complete IPv4 octets or IPv6 groups, such as `1.` or `10.4`) only scans the tokens of kinds that are already watched (Pods, Services, EndpointSlices, Nodes, Ingresses, Gateways) and starts no watch. A strong query (an address, CIDR or range, or a prefix with two or more complete parts) also starts the on-demand IP sources the cluster serves (ServiceCIDR, MetalLB IPAddressPool and BGPPeer, Multus NetworkAttachmentDefinition, CiliumLoadBalancerIPPool, CiliumPodIPPool, CiliumNode, Calico IPPool) and waits up to 800 ms for them to list; they then linger like any on-demand watch. A source that is still listing shows up in `pending`; one that cannot start because the watch budget is full is in `skipped` with `reason: "budget"`. |

`ref` is `{cluster, gvr, namespace?, name?, uid?}`; `gvr` is `v1/pods` or `apps/v1/deployments`. In `create` mode `ref.name` may be empty.

**Pinning a request to an object incarnation (`ref.uid`).** A UI that read an object and acts on it later must not hit a *different* object that was created under the same name in between (GitOps recreates things). When `uid` is set: `object.delete` sends `Preconditions{UID}` (the API server refuses a mismatch); `object.action` (including the Flux actions) and update-mode `object.apply` first read the live object and fail with code `conflict` and the message `object was replaced` when its uid differs, before anything is patched (`apply` also sends the uid in the PUT); `stream.open` with a `ref` (logs, exec, debug, port-forward) checks it before routing. `jobs.start` takes no object refs. Without `uid` nothing changes.

### Mutations: contexts and idempotency

- **Secrets are masked unless `reveal: true`.** `object.get`, `object.subscribe` and the `live` object of a conflict replace every Secret `data`/`stringData` value with `"__v8s_masked__"` (keys kept) and strip `kubectl.kubernetes.io/last-applied-configuration`. An update (`object.apply` or `object.dryRun` in `update` mode) that still contains the sentinel for a key keeps that key's live value, and a stripped last-applied annotation is kept; a sentinel for a key that does not exist is `bad_request`.
- **Every mutating request carries a client `requestId`** (`object.apply`, `object.delete`, `object.action`). The agent remembers the outcome (result or error) for 10 minutes; a repeat, even while the first is still running, returns that outcome without acting twice. A mutation runs under a 60 s timeout that does not follow the caller: a connection that drops mid-request neither aborts it nor drops its dedupe entry, so a retry after a reconnect replays the recorded outcome (waiters stop only when their own request ends). Dry runs are not deduplicated.
- **Reads and watches always use the read context.** For a mutation the agent asks `SelfSubjectAccessReview` on the read context (cached 60 s). If allowed, it runs there (a 403 from the read context's own call, after an allowed review, is the server's answer: `forbidden`). If denied and the cluster has a linked write context (`settings.links`) and `autoSwitchWrite` is on (default), it runs through the write context. If auto-switch is off, the error is `write_confirm`: the UI asks the user and retries with **`useWriteContext: true`**, which runs the request through the write context (honoured only when a link exists; without one the error is `forbidden`). Streams, jobs and dry runs take the same flag. Before the first routed write the agent compares the `kube-system` namespace uid of both contexts (cached); a mismatch is `link_mismatch` and nothing is written. A **401** from the write context, or a 403 for which the write context's own access review also denies or fails, is `write_unavailable` with the server's message; any other rejection through the write context (admission, quota, PodSecurity, validation) keeps its own code (`forbidden` / `invalid`) and message. If the review itself fails, the read context is tried and the server decides. Results carry `usedContext`. `access.check` follows the same rule: with auto-switch off, a check that only the write context allows is `{allowed: false, needsConfirm: true}`.
- Linked contexts are listed in `clusters.list` as `writeContext` of the read cluster, and are not listed as clusters of their own.

### Settings document

`{groups: {name: [clusterId]}, links: {clusterId: writeContextId}, autoSwitchWrite: bool (default true), stars: [gvr], bookmarks: [{name, url}], selection: [clusterId], columnLayouts: {gvr: {...}}, problemPrefs: {}, acks: {}, nodeShell: {clusterId | "*": {image?, namespace?, priorityClass?}}, portForwards: [{name?, ref, port}], protectedClusters: [clusterId]}`. Desktop persists it atomically (temp file + rename, mode 0600) to `os.UserConfigDir()/v8s/settings.json`; a corrupt file does not stop startup: it is renamed to `settings.json.corrupt-<unix>` and defaults are used; fake mode keeps it in memory unless `--settings` is given.

## Streams

Logs, exec, debug containers, node shells and port-forwards each get their own WebSocket, `GET /stream`, so a chatty log never delays view patches or keystrokes ([performance.md §8](performance.md#8-logs-shell-and-flow-streaming)).

1. The client sends `stream.open {type, …}` on the data socket. The agent validates the request, **routes it** like `object.action` (read context when allowed, else the linked write context; `write_confirm` / `useWriteContext` as in [Mutations](#mutations-contexts-and-idempotency)) and answers `{streamId, usedContext}`. A denied stream fails here.
2. The client opens `GET /stream` with `Sec-WebSocket-Protocol: v8s.v1, token.<hex>, stream.<streamId>` (same token and `Origin` rules as `/ws`; the id never appears in a URL). The id is single use and valid for 30 s; the agent echoes `v8s.v1`.

| `type` | Params | Notes |
| --- | --- | --- |
| `logs` | `ref` (a pod, with `container?`; or a workload / service, whose pods come from `spec.selector`) or `selector: {cluster, namespace, labelSelector}`; `follow`, `tailLines` (default 1000), `sinceSeconds`, `previous`, `timestamps`, `download` | One container: raw lines. Several (at most 50 containers, a snapshot of the started pods when the stream opens): merged by timestamp in the agent, every line prefixed `<pod>/<container>\t`. |
| `exec` | `ref` (pod), `container?`, `command?`, `tty?` (default true) | No command: shell discovery `/bin/bash` → `/bin/sh` → `/busybox/sh` (an attempt that fails because the binary does not exist, before any output, moves on). | `debug` | `ref` (pod), `target` (container), `image` | Adds an ephemeral container (`pods/ephemeralcontainers`), waits for it, execs a shell in it. |
| `nodeshell` | `node` (+ `cluster`) | See [operations.md](operations.md#node-shell). | `portforward` | `ref` (pod or service), `port` | Desktop and `v8s serve` only. Binds `127.0.0.1:<free port>`; **no socket**: the result carries `localPort` and `forwardId`. A service resolves to a ready backing pod (its `targetPort` mapped) and re-resolves, rebinding the same local port, if the pod dies. `portforward.list` / `portforward.stop` manage them; saved forwards live in `settings.portForwards`. |

**Logs frames.** Agent → client: binary frames of UTF-8 lines, batched at most 100 ms or 64 KiB. **Credit-based flow control**: the stream starts with 256 KiB of credit; the client adds more with the text frame `{"credit": n}` (bytes). The agent deducts every frame (it may overshoot by one frame) and stops sending, and so stops reading the API server's stream, while the balance is not positive. The stream ends with `{"end": true, "error"?}`. With `download: true` no socket is opened: the result carries `downloadUrl` (`/stream/download?streamId=…`), a single use `GET` (the id is the one-shot token; the `Origin` allowlist applies) that returns the whole log, merged the same way, as one `text/plain` response streamed straight from the agent.

**Interactive frames** (exec, debug, node shell). Client → agent: binary `[0x00][stdin bytes]`; text `{"resize": {"cols", "rows"}}`. Agent → client: binary `[0x01][stdout]`, `[0x02][stderr]` (a TTY merges them into stdout); text `{"ready": {usedContext, shell?, container?, pod?, attached?}}` first, and last `{"exit": code, "error"?}` before the close.

**Limits.** A stream that runs through a **write context** has a 15-minute idle timeout (any traffic in either direction resets it) and a 60-minute cap; the exit/end frame says which. Streams on the read context have none on desktop. A forward through a write context has the 60-minute cap only.

## Jobs

`jobs.start {requestId, type, params}` runs a long operation as an agent-owned job and answers `{jobId}` (a repeated `requestId` returns the same job for 10 minutes). Any denied, unroutable or invalid request fails the call itself, before a job exists. Every change of a job is pushed to every connected data socket as a `Job` frame (`{jobId, type, state: running|done|failed|cancelled, cluster?, subject?, startedAt, endedAt?, progress: [{at, message, item?, state?}], progressDropped?, error?, usedContext?}`; `progress` holds the last 200 entries); `jobs.list` returns the same states for a reconnecting client, and `jobs.cancel {jobId}` stops one.

| `type` | `params` | Behaviour |
| --- | --- | --- |
| `drain` | `{cluster, node, options: {ignoreDaemonSets (default true), deleteEmptyDirData, force, gracePeriodSeconds, timeoutSeconds (default 300), podSelector, disableEviction}}` | kubectl's drain logic (`k8s.io/kubectl/pkg/drain`): cordon, then evict through the Eviction API, retrying every 5 s while a PDB refuses (progress state `waiting-pdb`). `disableEviction` deletes instead of evicting (PDBs are not honoured). Pods without a controller need `force`, pods with emptyDir data need `deleteEmptyDirData`, else the job fails before evicting anything. Cancel, failure or a dead agent leave the node cordoned; re-running resumes. Routed through the write context when `patch nodes` is denied. |
| `helm.rollback` | `{cluster, namespace, name, revision, wait, timeout, cleanupOnFail, forceReplace, force}` | Helm 4 SDK `action.Rollback` as the user. |
| `helm.uninstall` | `{cluster, namespace, name, keepHistory, wait, timeout, cascade, force}` | `action.Uninstall`. |
| `helm.retry` | `{cluster, namespace, name, markFailed, wait, timeout, force}` | Re-runs the last upgrade from the stored chart and values; a stuck `pending-*` release needs `markFailed` first. |

A Helm action on a release carrying the labels `helm.toolkit.fluxcd.io/name` and `/namespace` fails the `jobs.start` call with `gitops_managed` (and a `hint`: use Flux reconcile / force / reset) unless `force: true`. (`forceReplace` is Helm's own `--force`.) Helm 4 reads and rolls back releases written by Helm 3 (same storage format; verified by test).

**Lifetime.** Jobs survive client disconnects. When the last data socket closes, running jobs continue for at most 15 minutes, then they are cancelled (a drain stays cordoned); a client connecting again cancels the countdown. State is in memory only.

## Problems view

`view.subscribe` with `gvr: "v8s/v1/problems"` (`protocol.ProblemsGVR`) serves the problems engine through the ordinary view engine, per cluster, with the same windowing, patches and cross-cluster merge as a resource list. Columns after `cluster`, `name` (the subject's name), `namespace`: `severity` (`critical` | `error` | `warning` | `info`), `severityRank` (0 critical … 3 info), `class`, `family`, `kind`, `title`, `message`, `since` (from the evidence), `lastChanged` (last change of severity, count or message), `count`, `source` (`trivy` | `kubescape` | `kyverno` | `hubble`), `acked` (`"true"` | `"false"`), `problemId` (the stable problem id used by `problems.evidence`, `problems.ack`, and `problems.unack`), `statusTone`. Filters: `family in`, `class in`, `severity in`, `cluster`, `namespace` (the query's `namespaces`), `text` (subject name), `acked eq`. Default sort `severityRank`, `lastChanged` desc, `name`; `since` is sortable for the "oldest first" order. Grouping by family, class, cluster or namespace is done by filters (the UI groups). The `problemId` cell is the problem's stable id, `hash(cluster, class, group/kind, namespace, name, discriminator)`, so a Deployment recreated by GitOps keeps its problem and its acknowledgement. (Wire row ids stay per-subscription like every view.)

The engine runs per agent instance and cluster over the tier-0 stores: a watch event marks its key dirty (plus the keys that join to it: EndpointSlice → Service → Ingresses, ReplicaSet → pods, Job → CronJob) and a pass every 250 ms re-evaluates only those keys; time-based conditions (`Pending > 5 min`, `OOMKilled within 1 h`) are woken by a deadline heap; a raised problem is held 30 s after its condition clears (hysteresis) and cleared at once when its object is deleted. Pod problems of one class in one workload roll up to a single row (`Deployment api: 2/3 pods CrashLoopBackOff`, the pods are `count` and evidence). Classes are switched with `settings.problemPrefs = {classes: {class: bool}, clusters: {clusterId: {class: bool}}}` (per-cluster wins over global over the class default); disabled classes are not evaluated and their problems are removed in the agent. `cluster.unreachable` is raised from the cluster state (`unreachable`, `reconnecting`, `auth-required`).

**Helm releases (`gvr: "helm.sh/v1/releases"`, virtual).** Built from Secrets with label `owner=helm` watched **metadata-only**; one row per release (its latest revision, stable id). Columns after `cluster`, `name`, `namespace`: `revision`, `status`, `updated`, `managedBy` (`flux:<ns>/<name>`), `statusTone`. Nothing is decoded for the list.

## Watch lifecycle

- **Tier 0** starts when a cluster is selected and runs until it is deselected: pods, nodes, namespaces, deployments, statefulsets, daemonsets, replicasets, jobs, cronjobs, services, endpointslices, ingresses, persistentvolumeclaims, Warning events, plus metadata-only watches of CustomResourceDefinitions and APIServices that invalidate discovery.
- **Any other kind** is watched on demand: view subscriptions hold references, one watch per (cluster, kind) however many views or clusters-in-scope use it. When the last reference goes, the watch **lingers 5 minutes**; each cluster has a budget of **96 watches**, and a new watch beyond it evicts the least recently used lingering one (tier-0 and referenced watches are never evicted; if nothing can be evicted the kind simply shows no rows from that cluster).
- **Object events**: an events view with `involved` holds a per-object events watch (key `v8s/v1/objectevents|<events namespace>|<Kind>|<namespace>|<name>`) with the same reference counting, but a **30 s** linger. It counts against the 96-watch budget and is LRU-evictable while lingering; a watch that fails (forbidden, timeout) is discarded at once instead of retrying during the linger.
- **Discovery** (aggregated discovery with legacy fallback) is cached per cluster, refreshed every 5 minutes and when a CRD or APIService changes.
- Rows appear **progressively** while a kind syncs: projected list pages and initial watch events are shown provisionally and reconciled by the reflector's final `Replace`. Fallback LISTs are paged (500).

## Hosted (`v8s server`)

The self-hosted multi-user mode speaks the same protocol over the same `/ws` and `/stream`; only authentication and the engine behind the socket differ. Design: [auth.md](auth.md#hosted), [performance.md §10](performance.md#10-hosted-mode-fan-out-and-sharing), [packaging.md](packaging.md#hosted-v8s-server).

### Connection auth

- `/ws` and `/stream` authenticate by the **session cookie** `__Host-v8s_session` (HttpOnly, Secure, SameSite=Strict, Path=/), not the token subprotocol. The client still offers `Sec-WebSocket-Protocol: v8s.v1` (400 without it); there is no `token.*` entry.
- **Strict origin**: `Origin` must equal the configured public URL; missing or different is 403. Chromium sends no `Sec-Fetch-*` headers on WebSocket handshakes (Firefox and WebKit do), so `Sec-Fetch-Site` is checked only when present (then it must be `same-origin`). A page cannot forge `Origin`, which is what blocks cross-site WebSocket hijacking. No cookie, or an expired/ended session, is **401**: the UI sends the browser to `/auth/login?return=<path>`. Ending a session (logout, expiry, eviction) closes its sockets.
- `GET /stream/download` needs the cookie and the single-use `streamId`; a present `Sec-Fetch-Site` must be `same-origin` (WebKit sends none on a programmatic `<a download>`, the Safari and iOS path). Every state-changing HTTP request (`POST /auth/logout`) must carry a matching `Origin`, or `Sec-Fetch-Site: same-origin` when `Origin` is absent; a foreign value is 403. `GET /api/me` rejects cross-site fetches.
- `Hello.mode` is `"hosted"`.

### Engines

Each identity (IdP subject + group set) has its own engine (cluster manager, views, problems, ops, streams, jobs, settings) whose cluster source is the server's cluster list filtered to the user's IdP groups (`adminGroups` see all; a cluster with `groups: ["*"]` is visible to every signed-in user). `clusters.list` returns only those clusters; `clusters.select` of any other id fails with `unknown cluster`. Access to a cluster is checked only when it is selected.

- The engine starts with the identity's first client and stops its watches **30 s after the last client closes** (a reconnect within the grace keeps them). Running jobs keep the engine record, without watches, until they end; the jobs manager's 15-minute no-client bound still applies.
- Several sessions of one identity share one engine; the cluster token used is the live session's token that lives longest.
- Settings are the same document as desktop, persisted per user as JSON under `dataDir/users/`.
- **Port-forward is disabled** (`stream.open` type `portforward` fails): a local port is meaningless on a server. HTTP preview ([operations.md](operations.md)) is not implemented yet.
- Kiosk clusters are read-only: mutations, exec/attach, logs, drain and Helm are unavailable, and access reviews answer "no" for writes.
- Requests carry `User-Agent: v8s/<version> (corr <hmac>)`. Read QPS is 20 (burst 40) per (user, cluster) with a 100 (burst 200) ceiling per cluster across users.

### HTTP endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /auth/login?return=/path` | start OIDC login (code + PKCE S256 + state + nonce; state/nonce/verifier stored server-side, bound to the browser by a short-lived `__Host-v8s_flow` cookie) |
| `GET /auth/callback` | verify the ID token (issuer, audience, nonce, expiry, JWKS signature), create the session, start the cluster-app flow |
| `GET /auth/cluster-login?return=` | re-run only the cluster-app flow (clusters `auth-required`); silent (`prompt=none`) first, interactive on `login_required` |
| `GET /auth/cluster-callback` | store the cluster app's ID token and refresh token in the session (memory only) |
| `POST /auth/logout` | delete the session and its tokens, clear the cookie (204) |
| `GET /api/me` | `{username, sub, groups, expiresAt, admin, clusterAuth: "ok"\|"required"}`; 401 without a session |
| `GET /healthz`, `GET /readyz` | liveness; readiness (identity provider reachable) |

The flows finish with a small HTML page that navigates client-side to `return` (a 302 from a redirect chain that began at the IdP is cross-site and would not carry the Strict cookie).

## Pods view (`gvr: "v1/pods"`)

Columns: see `PodColumns`. Sortable columns: every column of the schema. Filters: `statusTone in [...]` (tones as strings `"1"`…`"5"`), `status eq <reason>`, `node eq <name>`. `namespaces` restricts by namespace; `text` is a case-insensitive substring match on name; IP-like `text` (see `search`) also matches objects that hold a matching address, so `10.42.`, `10.42.0.0/16` or `10.0.0.5` filter the list by IP (the same on Services, EndpointSlices, Nodes and Ingresses). The `ip` column shows the pod's IPs (comma-separated) and sorts numerically; pods without an IP sort last. Default sort: `statusTone` severity (danger, warning, others), then `name`.

Status reason follows `kubectl get pods` (including native sidecars: restartable init containers count in `ready`/`containers`, and `SchedulingGated`): a container's waiting/terminated reason wins (`CrashLoopBackOff`, `ImagePullBackOff`, `OOMKilled`, `Error`, `ContainerCreating`), then `Terminating` if deleting, else the pod phase. Tone: danger for crash/pull/OOM/Error/Failed, warning for Pending/ContainerCreating/Terminating/not-ready Running, success for ready Running, info for Succeeded/Completed.
